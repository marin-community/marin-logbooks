# Paired continuation measurement protocol

This specifies measurements for the prepared replicated-versus-matrix comparison. It contains no training result. Numerical equivalence at `rtol=atol=1e-5` remains a diagnostic; practical assessment uses matched loss and measured speed. No acceptable loss gap has been declared.

## Step and data identity

The [completed full-restore audit](full-restore-counter-completed.json) independently verified stored and native counter 924 on all four processes, with checkpoint label 923 and configured-stream replay. Therefore, the first continuation loss is logged at `global_step=924`, and the final loss at 7629. The trainer finishes with counter 7630, after 6,706 additional updates. With global batch 8, the first configured data offset is 7,392 examples. Both runs must use the same verified initial counter, model, optimizer state, PRNG, data configuration and replayed first batch. Historical batch identity is not established by replaying the current configured stream.

The native callback runs at multiples of `StepInfo.next_step`, while metrics use the zero-based completed-update `StepInfo.step`. The configured evaluation interval is 763 updates. For a continuation from counter 924, scheduled evaluation labels are 1525, 2288, 3051, 3814, 4577, 5340, 6103, 6866 and 7629. Native final forced hooks can repeat the final evaluation. Preserve invocation/attempt identity and inspect duplicates; do not silently combine or drop them. The existing report code rejects duplicate evaluation labels when they appear as separate history rows.

## Loss comparison

Export complete W&B histories rather than sampled or smoothed curves. Preserve incremental local JSON logs and all attempt identities. Pair `train/loss` by verified global step, and `eval/paloma/c4_en/loss` by the same evaluation label and dataset. Retain other measured validation datasets. Report candidate minus original loss, raw paired curves and block summaries. Missing or nonfinite values remain explicit and cannot count as a successful comparison. For replayed steps after a restart, the main curve follows the verified checkpoint ancestry leading to each run's final state: use the execution whose resulting progress survives in that ancestry. Keep superseded executions as separate attempt curves, without averaging them into the main pair. If checkpoint/attempt ancestry cannot resolve an overlap, leave that step unresolved rather than choosing a record by timestamp alone.

The current preparation has one seed. Variation across steps or validation batches is descriptive and is not uncertainty across independent seeds. Do not report a seed-level confidence interval or declare loss equivalence from a single pair. Report the observed gap without inventing an acceptance margin. The older baseline at final step 7630 and canceled run at label 762 are not a matched comparison.

## Speed and memory

Record `throughput/duration`, `throughput/tokens_per_second` and `throughput/mfu`, together with logged device kind/count, theoretical hardware FLOPs and model FLOPs per example. Native step duration covers the compiled training step, including compilation when it occurs; it excludes input loading and subsequent hooks. Report `throughput/loading_time`, `throughput/hook_time` and end-to-end continuation elapsed time separately. Evaluation, checkpointing, compilation, restore and restart costs remain visible in end-to-end time.

Before seeing results, designate labels 1000–1099 as the first paired steady-step measurement window if neither run restarts or recompiles within that window and each has completed at least 20 updates since its latest process start or recompilation before label 1000. A restart before the window does not disqualify it when that condition is met. Report all steps as well as this window. If the window is ineligible for any reason, including insufficient warmup after an earlier restart or recompilation, retain it with that reason and use the first later common 100-update block, aligned to a multiple of 100, after at least 20 updates since the latest process start or recompilation in each run; either event resets this measurement warmup. These windows select measurements only; they never stop or shorten the final 7630-step schedule. Report the profiled update separately; profiling is configured at step 940 for one step.

For a complete window, report duration median and p10/p90 plus aggregate MFU `100 * (number_of_updates * global_batch * model_FLOPs_per_example) / (hardware_peak * sum(step_durations))`. Preserve the existing model FLOP count and correct hardware peak; do not include optimizer work in the numerator to inflate MFU. The absolute steady-training target remains above 5%. `hardware_peak` is the aggregate peak across the allocation. The existing v4-32 calculation uses 80,353,469,399,040 model FLOPs per update at batch 8 and 16 chips at 275 TFLOP/s each (4.4 PFLOP/s aggregate), giving a 5% threshold of approximately 0.36525 seconds per update. Verify the actual logged model FLOPs, device topology and peak before applying it. Synthetic optimizer timings and restore-audit memory do not establish training MFU or memory fit.

Use fresh online W&B runs for fresh processes. Keep per-attempt `_runtime` and timestamps; never concatenate runtimes across restarts as though uninterrupted. Only join restored progress after verifying checkpoint and data position, retain overlap/replayed work, and report restart overhead separately. A continuation's time-to-loss is not total training time from initialization. No loss target is chosen in this protocol.

## Remaining execution checks

Both prepared configurations enable native `crash_on_nan` and `crash_on_inf`, use the same global batch 8/final counter 7630, evaluation interval, profile settings and 256 GiB host memory. Configuration checks do not prove finite outputs or fit. Require all four successful restore/data reports, original saved-state synthetic-gradient and unchanged-state checks, and actual full-training memory/finite validation with fresh online logging before the loss comparison. Run the original and candidate sequentially. Preserve every-update Gram refresh, full geometry and source precision.

The saved-state check must include two distinct cases: evaluate the direction on the unchanged saved Gram/momentum state, and evaluate a full refresh/update using a fixed synthetic gradient. Preserve the original input state in both cases and report finite outputs and diagnostic differences. The unchanged-state case is a diagnostic only; training must still refresh every update. The historical `optimizer_cost.py` asserts equivalence before completing its saved-state comparisons, so it cannot be reused unchanged under the current loss-first criterion. Any corrected numerical entrypoint still needs its own online logging check, online CPU harness and exact source publication before one sequential TPU diagnostic. The saved-state entrypoint and its own online logging/CPU validation are now published in [saved-state-check-validation.json](saved-state-check-validation.json); its regional result remains pending.
